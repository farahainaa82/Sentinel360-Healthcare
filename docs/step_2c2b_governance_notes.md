## 1. Scenario Governance Principles

The following principles are **architectural constraints** for all future scenario engine development. They are not optional guidelines.

### 1.1 Estimation, Not Guarantee
- Scenario outputs are **estimates**, not forecasts guaranteed to occur.
- Every scenario output must carry an `estimate_confidence` field.
- Prohibited language: "Predicted outcome", "Guaranteed result", "Will achieve", "Definite improvement".
- Required language: "Estimated effect", "Plausible impact", "Association-based estimate".

### 1.2 Non-Causality Preservation
- **Association does not prove causation.**
- Cross-KPI effects must use language such as "Estimated association effect" or "Plausible impact based on observed correlation".
- Step 2B-4 relationship strengths may inform bounds but must not be treated as causal elasticities.
- Combined-interaction scenarios must carry the fixed governance warning: "Cross-domain effects are association-based only; no validated causal model exists."

### 1.3 Assumption Visibility
- Every assumption used in a scenario run must be recorded in an `assumption_log` output.
- Assumptions must be traceable back to `scenario_assumption_config.csv`, `scenario_assumption_definition.csv`, or user entry.
- The `assumption_audit_template.csv` structure must be populated for every run.

### 1.4 Data Immutability
- **Observed baselines must never be overwritten by user assumptions or scenario calculations.**
- Baseline values must be stored in immutable columns (e.g., `baseline_kpi_value`).
- Scenario-adjusted values must be stored in separate columns (e.g., `scenario_kpi_value`).
- Derived parameters must be recomputed from immutable baselines, not from scenario-adjusted values.

### 1.5 Baseline-Scenario Traceability
- Every scenario output row must contain both baseline and scenario values.
- Delta columns (`delta_value`, `delta_percent`) must be derived, not primary storage.
- The baseline source file and record IDs must be persisted for audit.

### 1.6 Provisional KPI Governance
- **kpi_003 (Bed Occupancy Rate)** and **kpi_005 (Patient Complaint Rate)** remain provisional (Conditionally Approved).
- Any scenario involving kpi_003 or kpi_005 must carry `provisional_kpi_warning = True`.
- When a provisional KPI is the **primary affected KPI**, scenario execution is **blocked**.
- When a provisional KPI is a **supporting KPI**, scenario confidence is reduced by 10% (multiplier 0.90).
- Provisional KPI scenarios must cap confidence at **Moderate**.

### 1.7 Contradiction Governance
- **Minor contradiction:** Scenario may proceed; confidence capped at Moderate; monitoring conditions included.
- **Material contradiction:** Scenario may proceed only as limited trial, low-regret comparison, sensitivity analysis, or monitoring-supported scenario. Confidence reduced by 15%. Management confirmation required.
- **Major contradiction:** Scenario execution **blocked**.
- No Major contradictions currently exist in the Required package population.
- Contradiction warnings must never be suppressed or removed.

### 1.8 No Automatic Approval
- The scenario engine may produce estimated effects; it may **not** produce approval decisions.
- All scenario outputs must require explicit human review before entering the approval workflow.
- No `approval_recommended` or `auto_approve` field may be generated by the scenario engine.

### 1.9 No Financial Calculation in 2C-2
- Cost, revenue, budget impact, ROI, or payback-period fields must **not** appear in Step 2C-2 outputs.
- Financial review is Phase 2C-3, with separate authority and separate inputs.
- Scenario outputs may reference resource counts or time durations, but must not attach monetary values.

### 1.10 Reproducibility and Audit
- Every scenario run must generate a unique `scenario_run_id`.
- Inputs, assumptions, code version, and timestamp must be persisted.
- Rerunning identical inputs must produce identical outputs (deterministic engine).
- The `scenario_run_manifest.json` must contain checksums of all input files.

## 2. Assumption Type Governance

### 2.1 Observed Baseline
- **Definition:** Values from historical analytical data.
- **Mutability:** Immutable.
- **User editing:** Prohibited.
- **Validation:** Must exist in source file; must have `calculation_status = Calculated`.
- **Example:** `baseline_required_staff`, `baseline_absenteeism_rate`.

### 2.2 User-Entered Intervention
- **Definition:** Values supplied by the scenario user to model an intervention.
- **Mutability:** User-editable within governed ranges.
- **Validation:** Must pass `scenario_assumption_range_config.csv` rules.
- **Audit:** Every change logged in assumption audit trail.
- **Example:** `additional_staff_count`, `assumed_absenteeism_reduction_pct`.

### 2.3 Approved Configuration
- **Definition:** Values from approved hospital policy or operational configuration.
- **Mutability:** Governance-editable only.
- **Validation:** Must be referenced in `config/` files with approved status.
- **Example:** Threshold boundaries from `kpi_threshold_config.csv`.

### 2.4 Derived Parameter
- **Definition:** Values computed from baselines or configurations.
- **Mutability:** Recomputed automatically; never user-edited.
- **Validation:** Formula must be deterministic and documented.
- **Example:** `baseline_staffing_coverage_pct` = available / required.

### 2.5 Fixed Governance Parameter
- **Definition:** Values set by scenario governance framework.
- **Mutability:** Governance-editable only; user changes rejected.
- **Validation:** Must match predefined values in `scenario_governance_rule_config.csv`.
- **Example:** `contradiction_confidence_multiplier` = 0.85.

## 3. Assumption Range Governance

### 3.1 Draft Analytical Ranges

All user-entered intervention assumptions have **Draft Analytical Range** classification. This means:
- The range is based on analytical judgment, not hospital policy.
- **Stakeholder validation is required** before the range can be considered operational.
- Conservative limits are applied.
- The range may be revised as empirical evidence accumulates.

### 3.2 Hard Limits

Hard limits are enforced by the scenario engine. Inputs outside hard limits are **rejected**.

| Assumption | Hard Min | Hard Max |
|------------|----------|----------|
| additional_staff_count | 0 | 50 |
| additional_covered_shifts | 0 | 30 |
| assumed_absenteeism_reduction_pct | 0 | 50 |
| replacement_coverage_pct | 0 | 100 |
| intervention_duration_days | 1 | 90 |
| temporary_staff_productivity_ratio | 0.5 | 1.2 |
| service_capacity_change_pct | -20 | 30 |
| arrival_change_pct | -30 | 20 |
| routing_efficiency_change_pct | 0 | 25 |

### 3.3 Soft Warning Limits

Inputs at or beyond soft warning limits trigger a warning but are **not rejected**.

| Assumption | Soft Warning |
|------------|--------------|
| additional_staff_count | > 20 |
| assumed_absenteeism_reduction_pct | > 30 |
| intervention_duration_days | > 30 |
| temporary_staff_productivity_ratio | > 1.0 |
| service_capacity_change_pct | > 20 or < -15 |

### 3.4 Invalid Input Actions

| Violation | Action |
|-----------|--------|
| Outside hard limit | Reject and prompt for correction |
| At/beyond soft warning | Accept with warning flag |
| Negative staff count | Reject (hard limit: 0) |
| Absenteeism reduction > 50% | Clamp to 50% and warn |
| Waiting time < 0 | Reject (inherent physical bound) |

## 4. Confidence Model

### 4.1 Allowed Confidence Levels in Phase 2C-2

| Level | Criteria | Allowed? |
|-------|----------|----------|
| **High** | Not achievable in Phase 2C-2 | **No** |
| **Moderate** | Baseline High confidence, no Material contradiction, no provisional primary KPI | Yes |
| **Low** | Partial baseline, Material contradiction, or provisional supporting KPI | Yes |
| **Insufficient Evidence** | Major contradiction, unsupported family, or monitoring-only | Yes |

### 4.2 Confidence Calculation (Conceptual)

```
base_confidence = baseline_confidence_factor
    × contradiction_multiplier
    × provisional_multiplier
    × missing_data_multiplier
    × assumption_extremity_multiplier
    × combined_scenario_multiplier

capped_confidence = min(base_confidence, Moderate)
```

All multipliers are defined in `scenario_confidence_rule_config.csv`.

## 5. Comparator Governance

### 5.1 Comparator Types

| Type | Intensity | Label Prohibition |
|------|-----------|-------------------|
| Baseline | 0 | Must not be labelled "Worst Case" |
| Conservative | 1 | Must not be labelled "Best Case" |
| Expected | 2 | Must not be labelled "Guaranteed" |
| Higher Intensity | 3 | Must not be labelled "Optimal" |
| Monitoring Only | 0 | Must not produce quantitative comparison |

### 5.2 Comparator Purpose

- **Baseline:** Reference condition for all delta calculations.
- **Conservative:** Low-regret trial; explores modest intervention.
- **Expected:** Plausible intervention aligned with package rationale.
- **Higher Intensity:** Stress-test; explores operational feasibility boundary.

## 6. Baseline Governance

### 6.1 Baseline Immutability

Baseline values:
- Must come from observed analytical data.
- Must not be substituted with arbitrary defaults.
- Must not be overwritten by user assumptions.
- Must carry `baseline_status` (Available / Partial / Unavailable).

### 6.2 Missing Baseline Handling

| Status | Action |
|--------|--------|
| Available | Proceed with standard confidence |
| Partial | Proceed with reduced confidence; document completeness |
| Unavailable | Block scenario execution; record `missing_input_reason` |

### 6.3 Baseline Fields

Every scenario baseline must contain:
- `baseline_id`
- `approval_package_id`
- `episode_id`
- `hospital_id`, `department_id`
- `baseline_start_date`, `baseline_end_date`
- `dominant_kpi_id`, `dominant_kpi_value`
- `supporting_kpi_values`
- `baseline_source_file`, `baseline_source_record_ids`
- `baseline_confidence`, `baseline_data_completeness`
- `baseline_provisional_flag`, `baseline_contradiction_severity`
- `baseline_created_at`, `baseline_version`

## 7. Exclusion and Monitoring

### 7.1 Excluded Packages

- 289 Not Required packages are **excluded from scenario execution**.
- They remain in the eligibility register with `scenario_engine_status = Exclude`.
- No records were deleted.

### 7.2 Monitoring-Only Packages

- Any package may be run in Monitoring-Only mode.
- Monitoring-Only mode produces **no quantitative scenario outputs**.
- It validates data availability and confirms operational conditions.

## 8. Audit and Versioning

### 8.1 Assumption Audit Trail

Every assumption change must be logged:
- `assumption_event_id`
- `scenario_run_id`
- `approval_package_id`
- `assumption_id`, `assumption_type`
- `previous_value`, `new_value`
- `unit`, `changed_by`, `changed_at`
- `reason`, `version`
- `source_reference`

### 8.2 Scenario Run Manifest

Every run must produce:
- `scenario_run_id` (UUID)
- `run_timestamp`
- `engine_version`
- `input_file_checksums`
- `assumption_set_version`
- `governance_rule_version`
